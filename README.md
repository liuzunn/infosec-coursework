## 实验一 · 熟悉网络环境

用 Windows 自带网络工具摸清本机网络状况，逐条记录并分析输出：

| 类别 | 命令 | 观察点 |
| :--- | :--- | :--- |
| 配置 | `ipconfig /all` | IP、子网掩码、网关、DNS、MAC |
| 连通 | `ping` | 本机回环、内网网关、外网 RTT |
| 路由 | `route print` | 默认路由、同网段直连 |
| 邻居 | `arp -a` | 网关 MAC、组播地址、动态/静态表项 |
| 连接 | `netstat -ano` | 监听端口、ESTABLISHED 连接、PID |
| 解析 | `nslookup` | DNS 服务器与解析过程 |
| 追踪 | `tracert` | 逐跳路径与延迟变化 |
| 端口探测 | `Test-NetConnection` | 23 / 443 端口的可达性 |

> **隐私处理**：原始输出中的内网 IP 统一替换为 `10.119.xxx.xxx`，物理地址替换为
> `XX-XX-XX-XX-XX-XX`，主机名替换为 `DESKTOP-XXXXXXX`。协议专用地址
> （`ff-ff-ff-ff-ff-ff`、`01-00-5e-*`、`224.0.0.*`）予以保留，因为它们是标准规定的，
> 与具体设备无关。

## 实验二 · 基本密码破解

复现 Office 文档「打开密码」的破解流程，并定量刻画口令强度。

### 实验设计

1. 用 python-docx 生成一份明文 Word 文档
2. 按 ECMA-376 敏捷加密（AES-256 + SHA-512，迭代 1000 次）分别用 3 / 4 / 5 位随机口令加密
3. 自编 Java 破解器，32 线程并行枚举候选口令
4. 命中后解密原文，验证还原一致（而非误判）

### 破解原理

Word 不保存明文口令，只存两个校验值（`EncryptedVerifierHashInput` /
`EncryptedVerifierHashValue`）。破解时对每个候选口令做同样的密钥派生：

```
H0 = SHA-512(salt ‖ password_UTF16LE)
Hi = SHA-512(LE32(i) ‖ Hi-1)        × spinCount
```

再用 H 解密校验值、比对哈希。命中即口令正确 —— 全程无需打开文档。

### 实测数据

| 口令长度 | 候选总数 | 命中序号 | 实测耗时 |
| :---: | ---: | ---: | ---: |
| 3 位 | 46,656 | 96.7% 处 | 1.01 s |
| 4 位 | 1,679,616 | 16.6% 处 | 4.08 s |
| 5 位 | 60,466,176 | — | 16 s 量级 |

实测速率约 **7.7 万次/秒**。候选空间按 36 倍递增，耗时同步放大 —— 口令长度是唯一的
有效防御维度。

### 字典 vs 暴力

另建一个 6 位弱口令文档（`abc123`），用 216 条常见口令字典尝试：**第 13 条命中，0.03 秒**。
同样的 6 位空间用暴力枚举需要约 2.18×10⁹ 次 —— 差 6 个数量级。

结论：**人类起的密码几乎必然出现在字典里**，长度比复杂度更重要。
